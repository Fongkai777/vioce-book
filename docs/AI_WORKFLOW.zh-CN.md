# AI 辅助开发流程

[English](AI_WORKFLOW.md) · [中文项目首页](../README.zh-CN.md)

## 开发过程

1. 将作业拆成可核验要求：语音输入、有依据的 RAG 回答、语音输出、检索质量、界面、文档与测试。
2. 按责任模块参考开源项目，而不是直接复制一个完整代码库。
3. 选择能展示来源、检索逻辑可确定性测试的最小架构。
4. 使用 AI 辅助起草实现，再通过单元测试、类型检查、生产构建、浏览器检查和获准的真实 API 冒烟测试验证。
5. 记录失败和限制，区分原型实现、已测事实与全面生产化建议。

## 关键工程判断

- 不只使用固定长度分段与纯向量召回，避免忽略作业强调的召回问题；增加章节结构、BM25 和排名融合。
- 引用页码来自解析结果，不由模型编造；缺少原始 PDF 的导入书明确显示未知页码。
- 语义与 BM25 分数不可直接比较，因此采用 RRF 融合排名。
- 将易误解的混合输入框换成明确的语音控制，正常转写直接进聊天并自动发送，异常文字保留供检查；建议问题仍可用。纯键盘自由提问入口仍是待补的无障碍能力。
- 书与索引保存在按账号隔离的本机 IndexedDB，明确告知不自动云端同步或备份。

## 提示词约束

模型接收检索段落、阅读偏好和预算内的完整或压缩历史，按读者语言回答，引用证据标签，在证据不足时说明限制。默认简洁、避免表格，适合朗读；明确要求详细时可展开。当前问题的格式要求优先于长期表达偏好，而偏好不能覆盖事实与能力边界。

## 验证要求

接受 AI 生成代码前应确认：

- 确定性逻辑有针对性测试。
- 密钥、上传与账号数据边界经过检查。
- API 请求形状与所用接口文档一致。
- 生产构建成功。
- 加载、错误、空状态与拒绝权限等用户可见路径经过实际操作。

自动化测试通过不代表语音硬件、答案语义或生产恢复已获保证。已进行和未进行的验证分别记录在[测试与评估](EVALUATION.zh-CN.md)，不将待测目标包装成实际结果。
