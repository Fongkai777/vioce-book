# AI 辅助开发流程

[English](AI_WORKFLOW.md) · [中文项目首页](../README.zh-CN.md)

## AI 的使用方式

- **实现与 Sites 部署：** OpenAI Codex，按明确的验收标准分小步实现。
- **独立评审与线上测试：** Claude 在不了解实现过程的情况下审查仓库，先测量疑似问题再报告；在 Chrome 中用合成语音经真实麦克风测试线上网站，并提出修复补丁。
- **我的职责：** 把作业转成验收标准，决定处理哪些发现，否决"用一个风险换另一个风险"的建议，并要求每项修改都有证据（基准测试、失败用例或线上观察）后才接受。

没有任何 AI 输出是凭它自己的判断合入的。下面每项修改都有复现方式和回归测试，或线上实测记录。

## 案例

### 1. 看起来没问题、却会卡住页面的排序函数

**发现方式：** 代码评审。BM25 对每个查询词都要扫描全部片段来计算文档频率，复杂度是 O(片段数² × 长度)。

**修复前先验证：** 用 1,500 个片段的合成书测试，每次提问在主线程上耗时 **1.8 秒**。

**修复：** 文档频率只算一次，并缓存每个片段的词频统计。确认中英文查询的分数与旧实现**完全一致**后才接受。结果：首次提问 0.24 秒，之后约 25 毫秒。后续提交又把统计结果存进 IndexedDB，重新打开书时无需再分词。

**判断：** 原代码能通过单元测试，因为测试只验证正确性、不验证开销。现在的回归测试同时检查耗时上限。

### 2. 服务器拒绝的请求也扣了额度

**发现方式：** 审查调用顺序。个人额度在全站预算检查之前就扣了，所以"网站繁忙"的 429 也会消耗读者的提问次数。

**修复：** 因服务器原因失败时（预算、暂停或并发拒绝，供应商报错，模型输出无效）退还额度；读者主动取消的请求不退；全站费用预留永不退还。

**判断：** 否决了"失败一律退还"。那样会让真实的供应商费用从预算里消失，也会让"取消"变成免费重试。

### 3. 登录防护三轮迭代，每轮都带来新的取舍

1. **最初：** 按 IP + 用户名限流。评审发现换 IP 就能绕过，而且从响应时间能判断用户名是否存在。
2. **第二轮：** 增加按账号和按 IP 的计数，用户名不存在时也做一次密码哈希。下一轮评审发现：默认用户名 `admin` 是公开的，任何人都能让管理员一直登不上；拿不到 Cloudflare 的 IP 请求头时，所有访客还会共用一个全站计数。
3. **第三轮：** 管理员不受跨 IP 的账号锁定，但保留 IP + 用户名和单 IP 限制；二次验证密码按会话单独计数；IP 请求头缺失或可疑时直接拒绝登录，并输出不含访客 IP 的诊断日志。

**判断：** 每一步加固都引入了测试没覆盖到的可用性风险。否决了两个建议：信任可伪造的 `X-Forwarded-For`，以及在没有对 Worker 运行时做基准测试的情况下提高 PBKDF2 迭代次数。剩余不足见[安全说明](../SECURITY.zh-CN.md)。

### 4. 单元测试替代不了的线上语音测试

离线测试全部通过，但在线上（v32）用真实麦克风测试时，7 题答错 2 题，英文提问得到中文回答，引用标签显示成 "CHORUS."。

**诊断：** 检索查询拼接了上一个问题和召回的早期回答，所以换了新话题仍会检索到旧话题的段落。直觉做法是给模型*更多*上下文；实际修复是把两件事分开：回答模型仍收到完整对话，但检索只用当前问题，除非它依赖上一轮（含代词、以 and/why/what about 开头、很短的追问）。

**否决：** 用大模型改写查询。它更通用，但每轮都会增加延迟和费用；启发式规则已经修复了实测发现的问题。

**验证：** 先离线重放同一段对话，再在线上 v33 重测。柴郡猫那题由错变对，英文提问改用英文回答；故事结局那题只部分改善，也如实记录。

### 5. 重测发现了下一个问题

同一轮 v33 重测中，语音回答被截断，提示 "Too many AI requests are running"。原因是两段语音同时请求，占满账号的两个并发名额，此时只要还有其他请求在运行就会返回 429。

**修复：** 逐段请求（上一段播放时下载下一段），只重试临时的并发 429，每日额度和预算限制不重试。

**经验：** 修完一个问题再做线上测试，就会暴露下一个。包括失败项在内的完整记录见[验证日志](EVALUATION-LOG.zh-CN.md)。

## 减少迭代轮次的提示方式

- **先说明需要什么证据：** "先测量再报告"、"给出失败用例"、"按相同顺序重放同一段对话"。这样评审给出的是数据而不是观点。
- **要求区分"已验证"和"可能存在"的问题，** 并给出每个问题的具体失败场景。
- **有取舍的修复，诊断和修改分两轮进行**（案例 2–4），决定权留在我手里。
- **要求文档和代码同一次修改：** 每个修复都同步更新更新日志、中英文文档和验证日志，避免文档与代码脱节。

## 长期工程选择

- 按章节结构切块，BM25 加向量检索，用倒数排名融合（RRF）。原因是固定长度切块配纯向量检索召回差，两种分数也无法直接比较。
- 页码来自解析结果，不由模型生成；未知页码明确显示为未知。
- 书籍和索引保存在按账号隔离的浏览器存储中，取舍已写入文档。

## 评审规则

AI 生成的代码只有在以下条件都满足时才接受：确定性逻辑有针对性测试；lint、类型检查和生产构建通过；密钥与数据边界经过审查；接口参数符合供应商当前文档；加载、出错、空状态和权限被拒等用户可见状态都实际操作过。

## 关于提交历史

约 30 个标题为 "Update Site source" 的提交，是 Sites 托管平台在发布时自动生成的。没有改写这些历史，因为强制推送会破坏已有链接。评审周期之后的提交都使用描述性信息。
